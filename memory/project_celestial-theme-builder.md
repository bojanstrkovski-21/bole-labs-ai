**Location:** `/home/bojanstrko/Projects/celestial-theme-builder/`

**Goal:** a tool (CLI first, GUI later) that takes a couple of hex color inputs (accent + background) and generates a complete desktop theme — GTK2/3/4+libadwaita, GNOME Shell, Cinnamon, XFCE4, Kvantum — by patching color-variable source files and re-running the forked theme's own existing build/install scripts. User is not a programmer (bash/Python basics only), wants something like Erik Dubois' accent-color scripts for celestial-themes, but self-built. KDE Plasma explicitly out of scope for now (separate, harder project — `.colors`/`kdeglobals`, no shared source with GTK).

**Scope pivoted to multi-base-theme (2026-07-21):** user compared `celestial-gtk-theme` against `jnsh/arc-theme` and `vinceliuice/Qogir-theme` to check if they share identical colors — they don't (same semantic/status colors and lineage, but each has its own background palette), so the user decided to support **both Celestial and Qogir** as separate generator targets rather than picking one. Building Qogir's pipeline first, Celestial second.

**Base theme #1 forked:** `zquestz/celestial-gtk-theme` (chosen initially over Qogir because it's SCSS-first — colors are variables in one place — vs what looked like Qogir's baked-in sed replacements across many pre-rendered files; that assumption about Qogir turned out to be wrong, see below). Cloned into `celestial-theme-builder/celestial-gtk-theme/`. Existing `converstion.md` in the project root is the exported prior planning chat (ends mid-way through a repo-wide grep dump, never finished the analysis — that analysis is what this session completed).

**Base theme #2 forked:** `vinceliuice/Qogir-theme`, cloned into `celestial-theme-builder/Qogir-theme/`. Turns out **simpler than Celestial**, not more sed-hacky as originally assumed from the old conversation export: GTK, GNOME Shell, and Cinnamon all `@import` the *same single* `src/_sass/_colors.scss` — one shared color source of truth, not three parallel systems like Celestial. Accent is `$selected_bg_color`, switched via `@if $theme == 'manjaro'/'ubuntu'` (only 2 built-in overrides beyond the `#5294e2` default — current upstream does NOT have the many-named-hue sed system the old conversation described, that may have been an older Qogir version or confused with a different vinceliuice theme). Background palette (`base_color`/`bg_color`/`fg_color`/`text_color`) is fixed regardless of accent — unlike Celestial, where every color variant (sea/aliz/azul/pueril) has its own full palette, not just its own accent. Build script `parse-sass.sh` compiles via `sassc`; accent selection happens by `sed`-patching a copied `_tweaks-temp.scss` (`$theme: default` → `$theme: manjaro`) before compiling, driven by `install.sh`'s `THEME_VARIANTS=('' '-Manjaro' '-Ubuntu')` array and `install_theme_color()` function. Pre-rendered per-accent SVG assets also exist (`assets-Manjaro/`, `assets-Ubuntu/`) that would need mirroring for a new accent, same non-SCSS-asset problem as Celestial's Kvantum/xfwm4.

**Key architectural finding:** Celestial isn't ~90 independent color roles to fill in — it's a small set of true *seed* hex values per subsystem (base/bg/fg/text per light-dark, one accent, a few fixed status colors), and everything else (borders, hover, insensitive, OSD, sidebar states, etc.) is *derived* via `lighten()`/`darken()`/`mix()`/`transparentize()` already written into the SCSS. The generator only needs to patch the seed values inside the `@if $color == "..."` branches (or add a new `$color == "custom"` branch) in three files — GTK, Cinnamon, and GNOME Shell each have their own separate color system/seed set, not a shared one. Kvantum (`.kvconfig`) and xfwm4 (`themerc-*`) are NOT SCSS — they need their own hex-substitution pass, no shared source with the Sass side.

**Preset format decided:** TOML, not JSON — see [[feedback-toml-over-json]]. Sectioned `[gtk]` / `[cinnamon]` / `[gnome_shell]` tables of seed hex values.

**Files that hold the seed/derived roles** (read and extracted this session):
- `celestial-gtk-theme/src/gtk/sass/_colors.scss` — GTK 3/4 core, 318 lines
- `celestial-gtk-theme/src/gtk/sass/_colors-public.scss` — exported `@define-color` list + Granite/Budgie fixed palette
- `celestial-gtk-theme/src/cinnamon/sass/_colors.scss` + `src/cinnamon/sass/custom/_panel.scss`
- `celestial-gtk-theme/src/gnome-shell/sass/40.0/_colors.scss` (shared by version dirs 38–48) + legacy `sass/3.28/_colors.scss` + `_high-contrast-colors.scss` (lower priority)
- App-specific extras in `gtk/sass/apps/_misc.scss`, `_gnome-3.0.scss`, `_xfce4.scss`, and `_libadwaita.scss` — mostly derived, one hardcoded exception (`question_bg_color: #ffea00` in Nautilus disk-space colors)

**Patch mechanism decided (Celestial, applies in spirit to Qogir too):** non-destructive — add the new colors as a genuine new named variant alongside the existing ones (not overwriting sea/aliz/azul/pueril or default/manjaro/ubuntu), named after the preset's own name/slug. Generation stays 100% the base theme's own original process: add the seed values as a new `@if` branch in `_colors.scss`, add matching entry-point files, then register the new slug in the theme's own build script (`parse_sass.sh`/`parse-sass.sh`) and installer (`install.sh`) exactly the way its existing variants are already registered — no bypassing or reinventing install/build logic.

**Branding/naming convention decided:** every theme this tool generates, regardless of which base engine (Qogir, Celestial, others later) actually built it, is installed under the **`Celestial`** name prefix — matching Celestial's own naming pattern (`${name}-${CapitalizedVariant}`, e.g. `Celestial-Sea`, `Celestial-Aliz`). So a Qogir-engine-built accent variant named `qogir_dark` installs as `Celestial-QogirDark`, not `Qogir-QogirDark`. This is the tool's own product branding, not a claim about which engine generated the CSS — Qogir-built variants are still built from Qogir's SCSS/install.sh, just labeled under the Celestial Theme Builder brand name. `scripts/generate_qogir_variant.py`'s `--theme-name` flag defaults to `"Celestial"` for this reason.

**Applying/verifying a generated theme touches several separate GTK config surfaces, not one** — relevant if this tool ever grows an "apply this theme for me" feature, since a generated theme being *correct* (right files, right colors) is a different thing from it being *visible*: `~/.gtkrc-2.0` (GTK2, owned/overwritten by nwg-look), `~/.config/gtk-3.0/settings.ini` + `~/.config/gtk-4.0/settings.ini` (theme name per GTK version), `~/.config/gtk-4.0/{gtk.css,gtk-dark.css,assets}` (GTK4/libadwaita — these are *symlinks* to a real theme's gtk-4.0 folder, not a name reference; GTK4 doesn't read gtk-theme-name at all), and `gsettings get org.gnome.desktop.interface gtk-theme`. All of these can independently disagree. Two concrete gotchas hit and confirmed this session, both worth remembering if this tool ever writes to these files directly: (1) `ln -sf newtarget path` does **not** replace `path` if `path` is already a symlink pointing at a directory — it silently tries to nest inside it instead (permission-denied on read-only dirs like `/usr/share/themes`), so any code updating these symlinks must `rm` first; (2) a base theme like Adwaita that ships **no `gtk-4.0` folder at all** (GTK4 renders it natively/built-in) means the correct state for those 3 files is *absent*, not repointed — nwg-look was observed leaving stale symlinks from the previous theme in place in that case rather than removing them.

## Base theme #4: Colloid-gtk-theme — now likely the preferred engine going forward

Mathematically monotonic, semantically incoherent — that's the general risk of any purely-numeric sort-and-interpolate shortcut applied to data that isn't actually one continuous scale to begin with. **Fixed properly**: `write_engine_native_palette()` now uses *only* the 4 true surface-role colors (`base_light`, `bg_light`, `bg_dark`, `base_dark` — explicitly excluding `fg`/`text`) as ramp anchors, blended with real per-channel linear RGB interpolation (`lerp_hex`/`interpolate_grey_anchors`) rather than nearest-value snapping, giving a smooth, visually coherent gradient anchored exactly at the source engine's own two real background tones. `order_by_luminance()`/`interpolate_grey_stops()` are left in the script but should **not** be reused for non-Catppuccin sources going forward — they're specifically for cases where the source data is already one genuine continuous ramp (Evergarden-style), not an arbitrary bag of same-role-different-context colors. **Propagating a preset color change touches 4 independent places per engine, not 1** — missing any one leaves a stale value that looks like a fresh regression later: (1) `presets/preset_evergarden_*.toml`'s `accent`+`success` fields (the nominal source of truth), (2) `references/evergarden_palettes.toml`'s `green` field per season — **this is the file Colloid's `--full-from-toml` path actually reads**, completely separate from the presets used by Qogir's `--preset` flag; editing only the preset TOML and not this reference TOML means rerunning the Colloid generator silently regenerates the *old* unmuted color, overwriting any manually-patched palette file. (3) Qogir's `Qogir-theme/src/_sass/_colors.scss` accent (`$selected_bg_color`) *and* status (`$success_color`) lines — both derive from the same source value and must be updated together or backgrounds/status pills go stale independently of the accent. (4) Colloid's `_color-palette-evergarden_<season>.scss` (`$default-light/dark` + `$green-light/dark`) and `assets.sh`'s `theme_color_dark/light` if-block + `button_close/max/min` case entry for that scheme — the latter two are separate idempotent-registration functions that only *add* an entry if missing, so a rerun after a color change **will not** update an already-registered case; must hand-edit or the xfwm4/window-button color silently stays on the old value forever.

**Reproduced, diagnosed, and fixed a serious new bug class in `generate_qogir_variant.py`'s `run_install()`: silent double-build via duplicate `-t` flag.** `run_install()` unconditionally does `cmd = ["./install.sh", "-t", slug, "-n", theme_name, *extra_args]` — if the caller's `--install-args` *also* includes `-t <same slug>` (as this session's regen loop did, out of habit from an earlier invocation style), Qogir's own arg parser appends the same theme to its internal `themes` bash array twice, so `install()` runs **twice** in one `install.sh` invocation for the identical `THEME_DIR`. The first pass builds correctly and ends with `cd ${THEME_DIR}/gnome-shell` (Qogir's own install.sh, line ~212, to set up local symlinks) — leaving the shell's cwd *inside* that just-built directory. The second pass's very first action, `rm -rf ${THEME_DIR}`, then deletes the directory tree the process's own cwd is still pointing into. Every subsequent `sassc` call in that second pass (GTK3 dark, GTK4 both, GNOME Shell — everything between the `rm -rf` and the *next* `cd` at line 212) fails with libsass's `Sass::Exception::OperationError: cwd gone missing` and aborts/core-dumps, **silently** — `install.sh` still prints its normal `Done.` at the end (it's a straight sequential script, no error-code check on the `sassc` calls), so the whole failure looked like a routine successful run in the terminal output at first glance and only produces empty/missing files, not a script exit failure. Confirmed by checking the installed theme directories directly: `gtk-3.0/gtk.css`, `gtk-3.0/gtk-dark.css`, `gtk-4.0/gtk.css`, `gtk-4.0/gtk-dark.css`, and `gnome-shell/gnome-shell.css` were **entirely absent** from `Celestial-Evergarden-Fall`/`-Spring`/`-Summer` after this run (Cinnamon's sassc call, which sits *after* the line-212 `cd`, was correctly unaffected — this asymmetry was the tell). **Fix: never pass `-t <slug>` in `--install-args` when calling `generate_qogir_variant.py` — `run_install()` already adds it. Only pass mode/color flags like `-c standard`.** Killed the corrupted background run, fixed the invocation, and regenerated all 5 seasons cleanly (verified via direct file-size + accent-hex grep on every one of the 5 CSS targets per variant, zero crashes on the clean rerun). **General lesson for this whole project: a bash installer printing "Done." is not proof of success when it runs several build steps sequentially without checking each one's exit code — always verify output files actually exist and contain the expected value after any regen, especially after any change to how a generator script's CLI args are assembled.**
